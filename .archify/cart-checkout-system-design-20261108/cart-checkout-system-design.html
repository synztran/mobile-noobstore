Answer

Ưu tiên trước mắt: khóa quyền RPC checkout, thêm idempotency key, rồi ghi order và voucher quota trong cùng transaction. Ba thay đổi xử lý ba rủi ro khác nhau; không cần migrate AWS để bắt đầu.

  1. PostgreSQL đang bảo vệ tồn kho bằng row lock trong RPC tạo order.
  2. API checkout chưa thấy idempotency key nên retry có thể tạo order mới.
  3. Voucher fields/usage và vài dữ liệu phụ được lưu sau RPC nên có thể lệch khi lỗi.
  4. Quyền submit_order trên production cần xác minh vì migration cũ grant cho public roles.

Applies toReview theo checkout commit 9c6c174; không kiểm tra quyền trên live database

1

Checkout hiện bảo vệ phần nào?

RPC giữ phần cốt lõi nhất trong một transaction: khóa stock, xác nhận số lượng, trừ kho và tạo order/items. Gift stock cũng được khóa cùng transaction khi dùng gift-aware RPC.12

Diagram structure
  • Browser browser
  • Checkout API api
  • PostgreSQL RPC db
  • Ghi side effects effects
  • browser → api · POST /api/checkout/submit
  • api → db · Gọi RPC sau khi tính lại giá và kiểm tra voucher
  • db → api · Commit order và tồn kho
  • api → effects · Lưu voucher, delivery, deposit, services; gửi thông báo
  • effects → browser · Trả order ID hoặc lỗi sau commit

Commit đã xảy ra không đồng nghĩa toàn checkout hoàn tất

Nếu bước sau RPC lỗi, client có thể nhận lỗi dù order và stock đã commit. Retry không có khóa nhận diện request cũ sẽ chạy lại luồng. Các side effects không quan trọng như notification nên có thể retry riêng; dữ liệu order/quota cần bảo đảm nhất quán.

Idempotency ngăn duplicate order ra sao?

Diagram structure
  • Gửi key K + checkout payload send
  • Tìm order đã gắn key K? lookup
  • Trả order trước đó existing
  • Trả cùng order ID result
  • Tạo order và gắn K trong transaction create
  • create → result · commit
  • existing → result · retry
  • lookup → create · chưa có
  • lookup → existing · có rồi
  • send → lookup · key K

Browser giữ cùng key cho một lần checkout; API gửi key tới database. Unique constraint làm hai request đồng thời cùng key hội tụ về một order. Key mới chỉ sinh khi khách bắt đầu một checkout attempt khác.

  1. Gửi key K ↗

    Dùng cùng key khi retry đúng lần checkout đó.

  2. Tra key ↗

    Nếu key đã có order, trả kết quả đã lưu.

  3. Tạo một lần ↗

    Unique constraint xử lý request đồng thời cùng key.

  4. Trả order ↗

    Chỉ tạo key mới khi khách bắt đầu lần checkout mới.

RLS và cart đang bảo vệ bằng gì?

Cart item routes PATCH/DELETE kiểm tra owner trước mutation; RLS policies cũng giới hạn cart_items qua cart cha. DELETE /api/cart nhận cart_id từ query nhưng route không kiểm tra owner tường minh; SSR client vẫn gắn session nên RLS là lớp thực thi hiện tại. Thêm owner check ở route giúp lỗi rõ và giữ defense-in-depth.

Checkout endpoint yêu cầu user đăng nhập, tính giá server-side và bỏ qua cart_id client khi quyết định cart nào convert. Điều đó giảm giả mạo cart ID nhưng không thay thế idempotency cho lần submit.4
